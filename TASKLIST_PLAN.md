### Task model contract

```ts
interface Task {
  id: string
  name: string
  scriptId: string
  interpreter: string
  arguments: string[]
  schedule: Schedule
  enabled: boolean
  lastRunAt: string | null
  nextRunAt: string | null
  status: TaskStatus
  createdAt: string
  updatedAt: string
}

type TaskStatus =
  | 'never'
  | 'scheduled'
  | 'running'
  | 'success'
  | 'failed'
  | 'disabled'
  | 'error'
```

Rules:

- `id` is generated by the repository and is immutable.
- `scriptId` references an existing managed Python script and is immutable after creation.
- `interpreter` is an executable path or resolvable command such as `python`.
- `arguments` are stored as individual argument values, not as an unparsed shell command.
- `lastRunAt` and `nextRunAt` use ISO 8601 strings, or `null` when unavailable.
- `createdAt` is immutable; `updatedAt` changes on every task update.
- `enabled: false` means the task must not execute from its Windows schedule.

### Schedule contract

```ts
type Schedule =
  | {
      type: 'once'
      runAt: string
    }
  | {
      type: 'daily'
      time: string // HH:mm, local Windows time
    }
  | {
      type: 'weekly'
      dayOfWeek: 0 | 1 | 2 | 3 | 4 | 5 | 6
      time: string // HH:mm, local Windows time
    }
  | {
      type: 'interval'
      every: number
      unit: 'minutes' | 'hours'
    }
```

MVP schedule rules:

- `once`: `runAt` must be a valid future datetime when created.
- `daily`: runs at the selected local Windows time every day.
- `weekly`: runs at the selected local Windows day and time every week.
- `interval`: `every` must be a positive integer; supported units are minutes and hours.
- Schedule calculations use the machine's local Windows timezone.
- Invalid or past schedule values are rejected before persistence or Windows task creation.

### Windows task naming convention

```text
ScriptsManagement\\<task-id>
```

The task ID is the stable identifier used to create, update, query, enable/disable, run, and delete the corresponding Windows Scheduled Task. User-provided names are display-only and are not used as command identifiers.

### Task lifecycle contract

| Operation | Required behavior |
|---|---|
| Create | Validate task, persist JSON, then create the Windows Scheduled Task. |
| Update | Validate changes, update JSON, then update the Windows Scheduled Task. |
| Enable/disable | Persist `enabled`, then enable or disable the Windows task. Disabled tasks use status `disabled`. |
| Run now | Execute the selected task immediately without changing its recurring schedule. |
| Delete | Delete the Windows task, then remove the task from JSON. |
| Startup/reconcile | Load JSON tasks and detect missing or mismatched Windows tasks. |

Failure rule: operations must return a structured error and must not report success when either JSON persistence or Windows Task Scheduler synchronization fails.

**Acceptance:** Model, schedule, naming, lifecycle, validation, and synchronization contracts are documented before implementation.

**Acceptance:** Clicking Run now launches the selected Python script through Windows Task Scheduler. ✅ Verified by real Windows smoke test (2026-08-13): created a task in the running app, confirmed registration in Task Scheduler, clicked Run Now (SUCCESS banner, task executed, Last Result recorded), deleted and confirmed removal.

Implementation notes:

- `TaskExecutor` separates frontend behavior from Tauri invocation.
- `TauriTaskExecutor` invokes `run_scheduled_task` with the stable `ScriptsManagement\\<task-id>` name.
- The UI tracks the active task, displays result/error feedback, and reloads tasks after execution.
- `TaskScheduler`/`TauriTaskScheduler` sync the full task lifecycle to Windows Task Scheduler: create registers via `create_scheduled_task`, edit re-creates, toggle calls `set_scheduled_task_enabled`, delete removes the registered task.
- `resolve_interpreter_path` resolves a relative interpreter (e.g. `python`) to an absolute path via `where.exe`; `get_log_directory` returns the app-local `logs` folder.
- schtasks constraints discovered in e2e: `/Create` with `/RU SYSTEM` fails non-elevated with "Access is denied" (tasks are created as the current user instead); weekly `/D` rejects numeric day values (builder maps 0-6 to SUN..SAT).
- Tauri `invoke` rejects with a plain string, so error handling surfaces the real schtasks message instead of a generic alert.
- Caveat: interpreter resolution uses `where.exe` in the app's launch environment; existing pre-fix tasks (e.g. `bill`) are not registered until edited or toggled once.
